# Tetris workflow router

Generated by `tools/check_workflow_adoption.py`; edit its adapter-selected template, not this output. Start with `AGENTS.md` and the current workspace index.

1. Read `skills/PROJECT_BASE_ADAPTER.json`. Keep `base_release` as the released compatibility identity; `shared_overrides.workflow_adoption` selects the separately reviewed operational source. Recheck remote main for drift, not automatic replacement.
2. Use a clean Base checkout at that `source_commit`. From the project root run:

   ```text
   python tools/check_workflow_adoption.py --base-repository <verified-Base-checkout> --protected-base <trusted-project-baseline-SHA> --external-approval true --check
   ```

   `true` requires actual current user approval or its verified merged receipt, not the manifest alone. In PR CI the baseline comes from the PR base when the adapter changes, otherwise from the base revision's adapter. Locally verify that the recorded baseline is an ancestor of fetched main; do not substitute a convenient SHA.
3. On failure, do not execute a shared route or claim validity. Read-only diagnosis and explicitly approved bounded repair remain allowed; rerun before routing. `--write` regenerates snapshot/dashboard with Base and the router with its project template after the same full contract check.
4. Read only the needed `effective_routes` in `skills/PROJECT_SKILL_SNAPSHOT.json`. Project-local precedence remains authoritative. For selected Base routes listed in `route_skill_ids`, read `skills/<skill_id>/SKILL.md` and needed references from the adopted operational `source_commit` (the verified checkout, or `git show <SHA>:<path>`). Never read a convenient different checkout. Unlisted new routes require an adapter review, not a fallback to latest main.

For player-facing work, the workspace index's **fun verification** section connects the adopted Base references to project requirements, actual consumers and existing playtest evidence. This router supplies paths, not game rules or HUMAN approval.
